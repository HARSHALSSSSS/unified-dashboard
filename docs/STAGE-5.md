# Stage 5: intelligence, automation, billing, administration, operations

Built on top of Stages 1-4 without touching their core: one central operational source of truth, with analytics / AI / automation / billing as **consumers** of it (events, read models, public module APIs).

```
Vendor -> Signup (free plan) -> Users/Roles -> Product -> SKU -> Marketplace Connection -> Listing -> Inventory -> Marketplace Order -> Central Order
-> Reservation -> Warehouse -> Pick -> Pack -> Ship -> Delivery -> Return -> Inventory Update -> Reports -> ANALYTICS -> RECOMMENDATION -> APPROVAL -> AUTOMATION
```
`tests/e2e/stage5-flow.test.ts` runs the Stage-5 half of this through the public API (on top of the Stage-4 e2e), including failure cases.

## Analytics (`/api/v1/analytics`, permission `analytics:read`)
* **Aggregation layer**: `analytics_daily_sales` (vendor × day × marketplace: orders, cancellations, units, gross/tax/discount/shipping, returns, refunds, delivered, shipped fulfillments + total ship seconds) and `analytics_daily_products` (vendor × day × variant). One idempotent SQL statement per read model rebuilds a window; a job does today + yesterday for every vendor every 15 minutes; `POST /analytics/rollups/rebuild` backfills (≤ 400 days, 31-day slices). **Dashboards never scan orders**: `overview` (vs the previous period of the same length), `products`, `marketplaces` read the roll-ups.
* **Health services** (live, vendor-indexed, bounded): `inventory-health` (low stock, stock-out risk, excess, aging, fast / slow movers; velocity = units actually sold, days of cover = available / velocity, **no sales ⇒ no forecast**), `product-health` (completeness score from description / brand / images / category / HSN / barcode / prices / cost + listing errors, unmapped order lines, active listings without stock), `business-health` (13 checks across orders, fulfillment, shipping, returns, marketplace, sync with counts, severity, sample ids and a 0-100 score).
* **Profitability** (`/analytics/profitability?groupBy=product|marketplace|order`): every component is `actual` (revenue, courier cost on the shipment, fee / penalty entered with `PUT /orders/{id}/financials`, processed refunds), `estimated` (fee profile %, the variant's **current** cost price, pending refunds) or `missing`. `contributionMinor` is **null while anything is missing**, with `missing[]`, `coverage` and `knownPartMinor` (revenue minus what is known, explicitly not a profit). Nothing is invented. Order-level costs are allocated to products by revenue share (stated in the response).

## AI (`/api/v1/ai`, permission `ai:use`, admin only by default)
* **Service boundary**: `AiProvider` (`narrate()` only). Default `rules` = no model. Optional `anthropic` provider (`AI_PROVIDER`, `ANTHROPIC_API_KEY`, `AI_MODEL`) may only re-word an already-computed answer from the facts it is given; on any failure the data-derived answer is returned. The model never queries or changes data and is never the source of truth.
* `POST /ai/ask`: question → intent → the SAME analytics the dashboards use → answer + `sources` + structured `data`. E.g. "Which products are likely to run out this week?" returns SKUs with available units, sales per day, days of cover and projected stock-out date. Unknown questions say what can be answered; they are not guessed. Rate limited; switchable (`ai.enabled` flag + vendor setting).
* `GET /ai/summary`, `GET /ai/anomalies` (z-score vs the previous 14 days with absolute and relative floors; no history ⇒ no anomaly).
* **Safety ladder** (`PUT /ai/settings`): `observe` (answers only) → `recommend` (default; recommendations stored, approving only records the decision) → `approve` (a human approval EXECUTES the action) → `automate` (only the action types listed in `automatedActions` run by themselves). Actions come from a **whitelist** (`set_reorder_level`; validated, reversible), every decision is audited, applied recommendations can be rolled back, open recommendations are de-duplicated and expire.

## Automation (`/api/v1/automation`)
Rule = trigger event → conditions (the rule-engine operators over flattened event facts) → whitelisted action. Triggers: 13 domain events (order created / needs attention, low stock, sync failed / dead-lettered, listing rejected, return received, marketplace disconnected / expired, warehouse exception, NDR, RTO ...). Actions: `notify`, `create_recommendation`, `retry_sync_job` (budgeted), `start_fulfillment` (reversible), `set_reorder_level` (reversible). Default mode `approval` (a person approves each run); `auto` runs immediately. **At most once per (rule, event)** (unique), throttled (120 / rule / hour), every run recorded with facts, result, error, approver, rollback data; `approve` / `reject` / `rollback` endpoints; `POST /rules/{id}/test` is a dry run; a rule with history can only be disabled. Switchable (`automation.enabled`).

## Billing (`/api/v1/billing`, platform side `/api/v1/admin/billing`)
Separate from commerce: it only LISTENS (`vendor.created` → free plan, `order.created` → usage) and is consulted through `enforceLimit` (marketplace accounts, products) which **only rejects when the platform enables `billing.enforce_limits` for that vendor** (limits are always reported in `GET /billing/usage`). Plans with limits / overage / features, subscription (change plan: a downgrade that does not fit is refused; cancel at period end), usage metering (monthly, atomic), invoices (hourly idempotent job; one per vendor + period; base + order overage + 18% tax; free invoices auto-paid), payments (idempotent per `providerRef`; failed → `past_due` + `billing.payment_failed`). A payment provider plugs into `recordPayment`; none is integrated (stated limit).

## Platform administration and feature flags (`/api/v1/admin`, `/api/v1/features/me`)
Platform staff only (`platform:*` permissions, never in a vendor role; support is read-only): platform overview, system health (DB probe, outbox age, stuck jobs), vendor summary, cross-tenant user search / disable (ends sessions) / enable, connector switches (global, with per-vendor override), failed jobs and failing integrations across tenants, feature flags with per-vendor overrides (`ai.enabled`, `automation.enabled`, `billing.enforce_limits`, `connector.<code>.enabled`, `beta.features`). Every change is audited; flags are read through `isFeatureEnabled` (vendor override > platform default > fallback) so no module needs to depend on admin. Cross-tenant audit trail: `GET /audit-logs` as platform staff.

## Resilience
API rate limiting (global + strict auth limits, Redis-backed), edge limits at the ingress; per-account marketplace token buckets and a **circuit breaker** (process-wide: opens after N consecutive outages, one half-open probe, only outages count) and **per-call timeout** (`CONNECTOR_TIMEOUT_MS`) in `ConnectorHost`; bounded retries with backoff and a capped `Retry-After`; sync jobs / webhook events with dead-lettering, manual retry and sweepers; idempotency keys on every authenticated mutation; graceful degradation: AI off ⇒ the rest works, a marketplace down ⇒ calls pause and jobs retry later, analytics served from roll-ups, a flag or plan limit never takes the commerce core down.

## Observability
Structured JSON logs (redacted), Prometheus metrics (HTTP, jobs, marketplace calls, DB pool + **business gauges** sampled every 30 s: sync jobs by status, stuck jobs, webhook events by status, outbox depth and age, account health per marketplace, pending approvals, DB round trip), OpenTelemetry traces, alert rules (`infrastructure/observability/alerts.yml`: error rate, latency, failed jobs, marketplace failures, outbox not draining, dead letters, stuck jobs, unhealthy connections, DB slow, worker down), a Grafana dashboard (`grafana-oms-overview.json`), health probes (`/health/live`, `/health/ready`), `GET /admin/system/health`.

## Deployment, backups, CI/CD
`infrastructure/k8s` (base: api, worker, scheduler, webhook-worker, migrate Job, Ingress, NetworkPolicy, HPA, PDB; overlays `dev` / `staging` / `production`), `.github/workflows/ci.yml` (verify + integration + docker) and `deploy.yml` (images tagged by sha → staging → manual approval → production; migrate Job first, rollout, smoke test). Production refuses an unsafe configuration at boot. Backups / restore / DR / migrations: `docs/deployment/BACKUP-RECOVERY.md`.

## Honest limits
* Connectors are simulator-verified only (`readiness.live=false`); real courier / payment-gateway / push providers are interfaces without an integration.
* The LLM narrator is optional and unverified against a live account here; the deterministic answers are what is tested.
* Load tests: no sustained-load run was executed in this environment; the design (roll-ups, keyset pagination, indexed statuses, row locks, pool/lock timeouts) is aimed at large vendor / order counts, and `docs/deployment` lists the scaling knobs.
* Still open from the security review: webhook timestamp replay protection, an SMTP mailer for production e-mail, PII retention jobs.
